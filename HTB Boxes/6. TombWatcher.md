**AD CS Basics**

**AD CS = Active Directory Certificate Services.**

**A Certificate Authority (CA) issues certificates.**

**A certificate template defines the properties of certificates that the CA can issue.**    

A normal LDAP query initially failed because deleted objects require the Show Deleted LDAP control.

Initial attempt:

```python
ldapsearch -x -H ldap://10.129.60.35 \
-D 'JOHN@tombwatcher.htb' -w 'Nhoj' \
```

3. Restore the Deleted Account
    

BloodyAD supports restoration under:

```python
bloodyad -H dc01.tombwatcher.htb -d tombwatcher.htb -u 'JOHN' -p 'Nhoj' set restore --help
```

Syntax:

```python
bloodyad set restore [-h] [--newName NEWNAME] [--newParent NEWPARENT] target
```

The first deleted cert_admin that was restored was:

```python
bloodyad -H dc01.tombwatcher.htb -d tombwatcher.htb \
-u 'JOHN' -p 'Nhoj' \
set restore 'CN=cert_admin\0ADEL:f80369c8-96a2-4a7f-a56c-9c15edd7d1e3,CN=Deleted Objects,DC=tombwatcher,DC=htb'
```

It was restored under:

```python
CN=cert_admin,OU=ADCS,DC=tombwatcher,DC=htb
```

However, this was the wrong deleted account.

Its SID was:

```python
S-1-5-21-1392491010-1358638721-2126982587-1109
```

This was important because the WebServer template later showed enrollment rights for RID 1111, not RID 1109.

Lesson:  
When multiple deleted accounts have the same name, always compare objectSID/objectGUID instead of relying on the username.

KEY LESSONS

1. GenericAll over an OU can be much more important than the OU itself. The useful objects may be recovered through inheritance or objects located within that OU.
    
2. Deleted AD objects can be enumerated with the LDAP_SERVER_SHOW_DELETED_OID control:
    

```python
-E '!1.2.840.113556.1.4.417'
```

3. Never identify duplicated deleted accounts only by sAMAccountName. Compare objectSID and objectGUID.
    
4. Certificate templates have separate concepts for:  
    Enrollment permissions  
    Template object-control permissions  
    Certificate properties  
    Extended Key Usage  
    Schema version  
    Subject/SAN behavior
    
5. A certificate template being visible does not mean the current user can enroll in it.
    
6. ESC15 can involve a V1 template with enrollee-supplied subject behavior. The certificate's normal EKU may still be Server Authentication.
    
7. A certificate obtained through ESC15 does not necessarily work with normal PKINIT. The successful route here was Schannel/LDAPS.
    
8. Certipy's LDAP shell is not a Windows shell.
    
9. Once authenticated as Administrator through Schannel, changing the Administrator password provides a simple path to a real WinRM shell.
    
10. When a certificate request returns:
    

```python
CERTSRV_E_TEMPLATE_DENIED
```

check the template's enrollment ACL before assuming the ESC technique itself failed.

11. When Certipy says:
    

```python
Failed to lookup object with SID 'S-1-5-21-...-1111'
```

that SID may be a stale/deleted principal. In this box, that clue led directly to the correct deleted cert_admin account.

12. The key discovery was matching the WebServer template's enrollment SID 1111 to the third deleted cert_admin object.
