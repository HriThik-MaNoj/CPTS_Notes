## Prioritizing our Efforts
- Report = main deliverable client pays for; no clutter, no 50+ pages of console output.
- Disclose everything, but focus time on high-impact findings (RCE, sensitive data disclosure).
- Consolidate minor issues into categories (e.g., 35 SSL/TLS variations, DoS in EOL PHP) instead of validating each.
- Use repeatable steps/scripts to filter scan noise and remove false positives.
- Lean on senior/mentor help to avoid rabbit holes.

## Writing an Attack Chain
- Shows how findings chain together (medium + medium = high risk); justifies severity ratings.
- Start with a summary, then walk each step with command output + screenshots.
- Reuse attack chain evidence in individual findings (copy/paste).
- Classic example: Responder (NBT-NS/LLMNR hash) → crack → foothold → Kerberoast → lateral movement → domain compromise.

## Sample Attack Chain (INLANEFREIGHT.LOCAL) - exam cheatsheet
1. `Responder` : spoof NBT-NS/LLMNR → capture NTLMv2 hash for user (bsmith).
2. `Hashcat -m 5600` : crack NTLMv2 hash offline → cleartext password → domain foothold (standard user).
3. `BloodHound-python` (`bloodhound-python -c All`) : enumerate domain, map attack paths.
4. `GetUserSPNs.py -request-user <user>` : targeted Kerberoasting → TGS ticket for SPN account.
5. `Hashcat -m 13100` : crack TGS ticket → service account password (mssqlsvc = local admin on SQL01).
6. `crackmapexec smb <host> -u mssqlsvc -p <pw> --lsa` : dump LSA secrets → srvadmin cleartext creds (admin over all servers).
7. RDP to MS01 as srvadmin → `query user` to find logged-in users (pramirez).
8. BloodHound : pramirez has DCSync rights (GetChangesAll/GetChanges).
9. `Rubeus dump /luid:0x... /service:krbtgt` : steal TGT → `Rubeus ptt` (pass-the-ticket) → confirm with `klist`.
10. `Mimikatz lsadump::dcsync /user:INLANEFREIGHT\administrator` : DCSync → Administrator NTLM hash → verify with CME.
11. `secretsdump.py ... -just-dc-ntlm` : dump all domain hashes → offline crack → domain password analysis.

## Writing a Strong Executive Summary
- Audience: non-technical person allocating budget — "if your parents can't understand it, rewrite".
- No acronyms (no SNMP, MitM), no vendor names, no referencing technical sections.
- Be specific with numbers ("25 occurrences of X" not "several").
- Keep it 1.5-2 pages max; describe what you accessed in plain terms (HR docs, banking systems).
- Describe root causes/process fixes ("what process broke down?"), not just "install 3 patches".
- Optionally set effort expectations (low/moderate/significant) for remediation.
- Use qualifiers to avoid absolutes ("testing seemed to go mostly unnoticed").
- Map each paragraph to a finding; don't cover every finding — focus on most impactful.
- Vocabulary swaps : VPN/SSH = "secure remote administration", password spraying = "one common password tried on many accounts", hash = "scrambled version of a password", DCSync = "replicating the password database".

## Summary of Recommendations
- Short / medium / long-term recommendations, each tied to a specific finding.
- Short = actionable fix (push patches); long = process fix (patch management program, SDLC review).
- Clients use this as a remediation roadmap — get it right or clients will ask you to prioritize.

## Findings
- Show off work, paint risk picture, give evidence to validate/reproduce, and remediation advice.

## Appendices
**Static (every report):**
- `Scope` : URLs, network ranges, facilities — auditors require it.
- `Methodology` : repeatable process showing thoroughness/consistency.
- `Severity Ratings` : criteria for each rating (if not CVSS); must be defensible.
- `Biographies` : consultant quals (required for PCI; builds client confidence).

**Dynamic (as needed):**
- `Exploitation Attempts & Payloads` : artifacts left behind; payloads dropped on disk — so client can clean up/distinguish you from real attacker.
- `Compromised Credentials` : list accounts (skip if all domain accounts — just say so).
- `Configuration Changes` : itemize everything changed (get approval in writing first) so client can revert.
- `Additional Affected Scope` : table of affected hosts too long for the finding itself.
- `Information Gathering` : external pentests — whois, subdomains, emails, breach data, SSL/TLS analysis, exposed ports.
- `Domain Password Analysis` : NTDS dump → Hashcat (wordlists + rules, brute-force ≤8 chars) → DPAT stats (hashes obtained, % cracked, privileged cracks, top passwords).

## Report Type Differences
- Internal pentest / external ending in compromise : full layout with attack chain.
- External only : info gathering + OSINT focus; no compromised creds/config changes/domain password analysis appendices.
- WASA : Executive Summary + Findings, emphasize OWASP Top 10.
- Physical/red team/social engineering : narrative format.
- Create templates per assessment type.
