> `meat` of the report

## Breakdown of a Finding
- Each finding should have same general type of information that should be customized to client specific circumstances.
- If a finding is written to suit several different scenarios or protocols, the final version should be adjusted to only reference the particular circumstances you identified. "`Default Credentials`" could have different meanings for risk it affects a Deskjet printer versus the building's HVAC control or another high-impact web application.
- `At a minimum` the following info should be included in each finding:
	- Description of the finding and what platforms the vulnerability affects
	- Impact if the finding is left unresolved
	- Affected systems, networks, environments or applications
	- Recommentations for how to address the problem
	- Reference links with addtional information about hte finding and resolving it
	- Steps to reproduce the issue and the evidence that you collected.
- Addtional, optional fields include:
	- CVE
	- OWASP, MITRE IDs
	- CVSS or similar score
	- Ease of exploitation and probability of attack
	- Any other information that might help learn about and mitigate the attack.

## Showing Finding Reproduction Steps Adequately
- `Break each step into ints own figure`.
- `If setup is required`, `capture the full configuration` so the reader can see the exploit config should look like before running the exploit. Create separate figure which shows what happens when you run the exploit.
- Write a `narrative between figures `describing what is happening and what is going through your head at this point in the assessment.
- After WT using our preffered tools, offer alternative tools that can be used to validate the finding ( `Just mention the tool and a reference link, dont exploit twice`)
- if you're trying to demonstrate the presence of a vulnerability in a particular web application or something else with a GUI (like RDP), it's important to capture either the URL in the address bar or output from an `ifconfig` or `ipconfig` command to prove that it's on the client's host and not some random image you downloaded from Google.
- Web app finding : give copy/pasteable payload, not just a Burp screenshot.
- Evidence must be defensible — proving cleartext auth needs login prompt + credentials visible in a Wireshark capture, not just the popup.
- Redact hashes/cleartext passwords (report gets passed around). Clean up browser (no bookmarks bar/unprofessional extensions).

## Effective Remediation Recommendations

#### Example 1
- `Bad`: Reconfigure your registry settings to harden against X.
- `Good`: To fully remediate this finding, the following registry hives should be updated with the specified values. Note that changes to critical components like the registry should be approached with caution and tested in a small group prior to making large-scale changes.
    - `[list the full path to the affected registry hives]`
        - Change value X to value Y

#### Rationale
- `Bad` example is lazy - squanders a learning opportunity, frustrates reader with hours of homework.
- `Good` example includes specific steps + warning that registry changes carry risk (client will blindly follow advice and hold you accountable if it breaks something).
- Do the research : shows competence in report review, builds client confidence, earns repeat business.

#### Example 2
- `Bad`: Implement `[some commercial tool that costs a fortune]` to address this finding.
- `Good`: There are different approaches to addressing this finding. `[Vendor]` has published a workaround as an interim solution (link in references). Alternatively, commercial tools can disable the vulnerable functionality, but may be cost-prohibitive.
- `Rationale`: Bad gives no path without spending money client may not have; alternative (even if a band-aid) buys time until official vendor fix.

## Selecting Quality References
- `Vendor-agnostic` sources preferred (Cisco ref only makes sense for ASA vulns, not general writeups).
- Thorough walkthrough with workarounds/mitigations — no paywalls or partial content.
- Get to the point quickly — no NIST 800-53/RFC dumps, no recipe-blog fluff.
- Clean websites (no ads/crypto miners).
- Bonus : write your own blog material — research helps explain impact, and you won't send clients to a competitor.

## Example Findings
- Finding layout: detailed description, impact if unfixed, affected hosts, generic remediation (no vendor tools, several options), references from reputable sources (not personal blogs).
- Formatting: tabular OR heading-separated — readability is paramount, whatever makes findings easy to pick out.
- Examples: Kerberoasting (CVSS 9.5, whole domain, enable AES), Tomcat Manager weak/default creds (CVSS 9.5, restrict access, change defaults).

## Poorly Written Finding (avoid)
- Sloppy formatting (broken CWE link), missing CVSS score if template uses it.
- Description doesn't explain issue/root cause; security impact vague and generic.
- Remediation not clear/actionable.
- Ask : why do I care? What do I do? Educate the reader on the attack (they may never have heard of Kerberoasting).
