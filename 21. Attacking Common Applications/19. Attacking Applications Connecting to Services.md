- # Attacking Applications Connected to Services

## Overview
Applications often connect to external services (e.g., databases, APIs) using **connection strings** that may contain hardcoded credentials. If these credentials can be extracted, they may allow:
- Access to the connected service.
- Password reuse attacks against other services.
- Lateral movement or privilege escalation.

---

# ELF Executable Examination

## Scenario
A binary (`octopus_checker`) attempts to connect to an **MS SQL Server** using **ODBC**.

```bash
./octopus_checker
```

Output:

```text
Attempting Connection...
[unixODBC][Driver Manager] Can't open lib 'ODBC Driver 17 for SQL Server'
```

This indicates the application is using **SQLDriverConnect()** to connect to SQL Server.

---

## Why Use GDB?

Use **GDB (GNU Debugger)** to inspect a compiled binary at runtime.

Load the binary:

```bash
gdb ./octopus_checker
```

(Optional) Use Intel assembly syntax:

```gdb
set disassembly-flavor intel
```

Disassemble the `main` function:

```gdb
disas main
```

---

## Finding the Connection String

Look for a call to:

```asm
call SQLDriverConnect
```

The connection string must exist in memory **before** this function is called.

### Set a Breakpoint

```gdb
b *<address_of_SQLDriverConnect>
```

Example:

```gdb
b *0x5555555551b0
```

Run the program:

```gdb
run
```

When execution pauses, inspect the registers.

Example:

```text
RDX:
DRIVER={ODBC Driver 17 for SQL Server};
SERVER=localhost,1401;
UID=username;
PWD=password;
```

Recovered credentials:

```text
username:password
```

> **Exam Tip:** Connection strings are often stored in registers or memory immediately before `SQLDriverConnect()` is called.

---

## Why Not Just Use `strings`?

Some applications build connection strings dynamically.

Example:

```cpp
connection = "SERVER=" + host + ";UID=" + user + ";PWD=" + pass;
```

The full string may only exist **during execution**, making runtime debugging necessary.

---

# Registers (x86-64 Calling Convention)

Function arguments are passed via registers:

| Argument | Register |
|----------|----------|
| 1st | RDI |
| 2nd | RSI |
| 3rd | RDX |
| 4th | RCX |
| 5th | R8 |
| 6th | R9 |

Check these registers before sensitive function calls.

---

# DLL (.NET Assembly) Examination

A `.NET` DLL can often be **decompiled** back into readable C# code.

Useful tools:

- dnSpy
- ILSpy

Instead of analysing assembly, inspect the source directly.

Example:

```csharp
string conn =
"Server=localhost;
User ID=sa;
Password=P@ssw0rd!";
```

Database credentials may be hardcoded inside the source.

---

# Credential Reuse

Recovered credentials should be tested against other services such as:

- MSSQL
- SMB
- WinRM
- RDP
- SSH
- Web applications

Password reuse is common in enterprise environments.

---

# CPTS Cheat Sheet

## Native Binaries (ELF/EXE)

- Identify database-related functions.
- Look for:
  - `SQLDriverConnect`
  - `SQLConnect`
  - Other DB connection APIs
- Set a breakpoint before the connection function.
- Inspect registers/memory for the connection string.
- Extract `UID` and `PWD`.

## .NET Applications

- Open with **dnSpy** or **ILSpy**.
- Search for:
  - `connectionString`
  - `Server=`
  - `UID=`
  - `PWD=`
  - `Password=`
- Recover hardcoded credentials directly from the decompiled code.

# Key Takeaways

- Applications often contain **hardcoded service credentials**.
- Runtime debugging can reveal credentials that are **not visible with `strings`**.
- Break execution **before** connection functions such as `SQLDriverConnect()`.
- .NET binaries are much easier to inspect using **dnSpy** or **ILSpy**.
- Always test recovered credentials for **password reuse** across the environment.
