# osTicket
## What it is

- Open-source support ticketing system (like Jira/OTRS/Request Tracker/Spiceworks).
- Written in PHP, MySQL backend. Runs on Windows or Linux.
- Integrates email/phone/web-form inquiries into one web interface.
- Widely deployed (schools, universities, gov, companies) — don't dismiss it as "just a helpdesk."

## Why it matters on an assessment

- Support portals are a common **external attack surface** that gets overlooked.
- Even when the app itself has no juicy CVEs, the _workflow_ around it (humans processing tickets) is the real vulnerability.
- Key idea: **User Input → Processing → Solution**
    - User input: anyone can open a ticket, including us. Great pretext for social engineering ("play dumb," report a fake issue).
    - Processing: staff reproduce issues internally — may leak internal details/usernames via email threads.
    - Solution: escalations often loop in other staff → more email addresses/usernames for OSINT or spraying.

## Footprinting / Discovery

- Nmap won't fingerprint it — just shows web server banner (Apache/IIS).
- Look for:
    - Cookie named `OSTSESSID`
    - Footer text "powered by osTicket" or "Support Ticket System"
    - EyeWitness screenshots showing "Support Center" page (new ticket / check ticket status)
- Typical URLs:
    - `http://support.<target>/` — public support center
    - `http://support.<target>/open.php` — open new ticket
    - `http://support.<target>/scp/login.php` — staff control panel login

## Known vulnerability classes (exploit-db)

- Remote file inclusion, SQLi, arbitrary file upload, XSS
- **CVE-2020-24881** — SSRF in osTicket v1.14.1 → can be used to hit internal resources / internal port scan

## Technique 1 — Harvesting a valid company email via ticket creation

1. Go to `/open.php` on the support portal.
2. Submit a new ticket (pick any help topic, e.g. "Feedback"; issue summary can be generic, e.g. "Your site is slow").
3. osTicket returns a **ticket ID** (e.g. `940288`) and often auto-generates an internal email alias tied to it, e.g. `940288@<target-domain>`.
4. This is now a **valid, receivable company email address** you control (via the ticket portal inbox).
5. Use this email to sign up for other exposed company services that require email verification:
    - Slack, Mattermost, Rocket.Chat, GitLab, Bitbucket, wikis, etc.
6. Check the verification email by logging back into the ticket / checking replies in the ticket thread.
7. Reference: this is the technique behind HTB's "Delivery" box.

## Technique 2 — Credential reuse + support agent social engineering leak

Scenario workflow (external pentest):

1. **OSINT / breach data**: Use a tool like Dehashed to pull leaked creds for the target domain.
    
    ```
    sudo python3 dehashed.py -q <target-domain> -p
    ```
    
    → yields email, username, cleartext password, name, source DB per hit.
2. **Subdomain enumeration** to find exposed portals, e.g.:
    
    ```
    vpn.<target>support.<target>auth.<target>dev.<target>...
    ```
    
    Check each — most are dead, but `support.*` (osTicket) and `vpn.*` (e.g. Barracuda SSL VPN, often no MFA) are common live hits.
3. **Credential testing** on the osTicket staff login (`/scp/login.php`, accepts email or username):
    - Try leaked username+password combos.
    - Also try the **email address** as the login (osTicket accepts either) — a password that failed with username may work with email format.
4. Once logged in as a support agent, look at ticket history — even with no open tickets, check **closed tickets**.
5. Look for conversations where:
    - An employee claims to be locked out (e.g., VPN access) and asks for a password reset.
    - The agent resets to a **standard "new joiner" password**.
    - The employee asks for a phone call (proper practice) but the agent **sends the password directly in the ticket** (mistake — this is the leak).
6. **Pivot**: try that password directly against the exposed VPN portal (password reuse likely if user hasn't changed it).
7. If it's confirmed as a **standard new-joiner/reset password org-wide**:
    - Build a company user list (e.g., via `linkedin2username`).
    - Password-spray the VPN (or other externally exposed auth) with that single standard password.
8. Also loot the osTicket **address book** — export all emails/usernames found there for future spraying/OSINT.

## Defensive takeaways (useful for report writing too)

- Limit externally exposed applications where possible.
- Enforce MFA on all external portals (VPN, webmail, etc.).
- Security awareness training — don't use corporate email for third-party signups.
- Strong AD/app password policy — block weak patterns (welcome/season/month/company name variants).
- Force password change on first login; expire passwords periodically.
- Never send a password directly through a ticket/chat channel — verify identity out of band (phone/video) instead.

## Quick mental checklist for future engagements

- [ ] Fingerprint support portal (cookie name, footer, login page path)
- [ ] Check exploit-db / CVEs for the specific version if identifiable
- [ ] Try opening a ticket → grab auto-assigned email → test against other exposed signup portals
- [ ] Run breach-data lookups (Dehashed or similar) against target domain
- [ ] Enumerate subdomains, identify live auth portals (VPN, support, etc.) — note MFA status
- [ ] Try leaked creds against staff login using both username AND email formats
- [ ] Review closed tickets for leaked resets/passwords sent in-band
- [ ] Export address book contacts for spraying/OSINT
